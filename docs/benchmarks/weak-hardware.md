# Weak-hardware benchmark (plan task 43)

Does FileX stay usable on a small x86-64 box with 2-4 GB of RAM? Measured 2026-10-13 with the
images built from `d88e6fd` (image ids below), through the real API, on a separate stack whose
containers all share one memory and CPU cap.

**Short answer:** yes. With every profile on, the whole stack idles at **175 MB** and the
worst job mix peaks at **1.05 GB**. At a 2 GB / 2 CPU cap, none of the 138 jobs failed and none
were OOM-killed. The ADR-0002 estimates (3.1 GB default, 2.4 GB low-memory, 1.1 GB core-only)
were 2-3x too pessimistic. The one real limit is Calibre's PDF output for long books, covered
in [Calibre long-book cap](#calibre-long-book-cap).

## Setup

- **Host:** the dev PC (Windows 11, Docker Desktop 29.8.2, WSL2 kernel 6.18, 8 vCPUs and 16 GB
  for the VM), with other workloads running at the same time. Its cores are much faster than a
  typical low-power home-server CPU, so read the **times** as a lower bound (see
  [CPU note](#cpu-note)). **Memory** numbers do not depend on CPU speed and carry over as they are.
- **Stack:** `compose.yaml` plus `scripts/bench/weak-hw.compose.yaml`, project `filex-bench`,
  port 8090, its own volume and internal subnet, `FILEX_AUTH=none`. Each container keeps its own
  compose limits (`mem_limit`, `cpus: 1.5` per worker). In addition, every container sits under one
  parent cgroup, `/filex-bench`, with `memory.max`, `memory.swap.max = 0` and `cpu.max` set to the
  machine size. So the stack as a whole cannot use more than 2 GB / 2 CPUs (or 4 GB / 4 CPUs),
  as on a small box with no swap.
- **Configs:**

  | Run | Cap | Profiles | `FILEX_MEM_CORE / _OFFICE / _OCR / _EBOOK` | Other |
  |---|---|---|---|---|
  | 2 GB | 2048 MB, 2 CPUs | `office,ocr,ebook` | 768m / 1g / 1g / 1g (low-memory preset) | `FILEX_MAX_PIXELS=50000000`, `FILEX_MAX_PAGES=1000` |
  | 4 GB | 4096 MB, 4 CPUs | `office,ocr,ebook` | 1g / 1536m / 1536m / 1g (defaults) | defaults |
  | 2 GB core | 2048 MB, 2 CPUs | none (core only) | 768m | `FILEX_CONCURRENCY` 1 and 2 |

  All runs use `FILEX_CONCURRENCY=1` and `FILEX_HEAVY_SLOTS=1` unless the table says otherwise.
- **Measurements:**
  - **Wall time** is client-side, from upload start to `SUCCEEDED`, polled every 0.25 s.
  - **Step time** is the worker's own `duration_s` log field.
  - **Peak memory** is cgroup v2 `memory.peak` (anon plus page cache) per container and for the
    whole stack. It is reset before each job, after the stack's page cache has been reclaimed
    (`memory.reclaim` on `/filex-bench` only), so it shows what that one job brought in.
  - **OOM kills** come from `memory.events`, plus each container's `RestartCount` and `OOMKilled`.
  - **Idle** is the median of 5 `memory.current` samples taken 45 s after start.
- **Reps:** 3 per case, interleaved (rep 1 of every case, then rep 2, and so on), so background
  load on the dev PC affects every case alike. Tables show the median, with min-max in brackets.
- **Inputs:** `tests/corpus` plus `generated/` (`python scripts/make_corpus.py --large`). The long
  EPUBs are generated by the bench script, sized by the tool's own `estimated_pages`.
- **Images:** api `3c44672a1fce`, worker-core `c7626d1b4117`, worker-office `771294e25b41`,
  worker-ocr `b5f10956d76e`, worker-ebook `272943cd6792`. The `redis` service image was being
  switched to Valkey in the working tree during the session. Its footprint is 3-10 MB either way,
  so this does not change any total.

Reproduce:

```sh
python scripts/bench/weak_hardware.py stack --mem-mb 2048 --cpus 2 --preset low --reps 3 --out r2g.json
python scripts/bench/weak_hardware.py stack --mem-mb 4096 --cpus 4 --preset default --reps 3 --out r4g.json
python scripts/bench/weak_hardware.py stack --mem-mb 2048 --cpus 2 --preset low --only NONE --mix-heavy --heavy-slots 0 --out hs0.json
python scripts/bench/weak_hardware.py stack --mem-mb 2048 --cpus 2 --preset low --profiles "" --concurrency 2 --only "merge 2x10p" --burst 3 --burst-case 200MB --out core-c2.json
python scripts/bench/weak_hardware.py calibre --pages 150 230 300 400 475 --configs 964:1024 1600:1536 1600:2048 --reps 3 --out cal.json
python scripts/bench/weak_summary.py r2g.json r4g.json      # Markdown tables
python scripts/bench/weak_summary.py --calibre cal.json
```

The script brings the stack up and takes it down again with its volume. It also creates and
removes a short-lived privileged helper container (`filex-bench-probe`, no network) and the
`/filex-bench` cgroup. It needs Docker's cgroupfs driver with cgroup v2; Docker Desktop and plain
dockerd both qualify. It never touches other compose projects. One `stack` run with 3 reps takes
about 12 minutes on the dev PC.

## Results

### Idle memory

| Set | Idle (memory.current) | Spec 5.1 target |
|---|---|---|
| api | 48 MB | |
| redis | 3-4 MB | |
| worker-core | 30 MB | |
| **Always-on core (api + redis + worker-core)** | **83 MB** | ≤ 350 MB: met |
| worker-office / -ocr / -ebook, each | 30-32 MB | ≤ 150 MB each: met |
| **Whole stack, all profiles** | **175 MB** | |

Workers start their engines in a fresh child per step and keep none loaded. After every job,
each worker's anonymous memory went back to 29-30 MB, and the api's to 48-59 MB. Idle was the
same at the 2 GB and 4 GB caps.

The 2 GB and 4 GB columns are the same within noise. Each worker is capped at 1.5 CPUs, and
these engines mostly run on one core, so a 4 CPU cap buys nothing for a single job. Spread
between reps is under 5% except for the 200 MB compress, at ±10%. Overhead (wall minus step,
which includes the upload) is 0.01-0.3 s, and 1.2 s for the 200 MB upload.

### Heavy jobs at once (2 GB, 3 reps)

Three jobs submitted together: office.to-pdf DOCX 20 p, ocr.pdf, and ebook.convert EPUB → PDF.

| Mix | `FILEX_HEAVY_SLOTS` | Last job done, s | Stack peak MB | Failed / OOM |
|---|---|---|---|---|
| DOCX 20 p + OCR 3 p + book 200 p | 1 | 10.0 (9.8-10.0) | 938 | 0 / 0 of 9 |
| DOCX 20 p + OCR 50 p + book 228 p | 1 | 81.1 (80.9-81.8) | **1045** | 0 / 0 of 9 |
| DOCX 20 p + OCR 50 p + book 228 p | 0 (off) | 76.9 (76.7-76.9) | **1237** | 0 / 0 of 9 |

The heavy slot works: with it, no two heavy peaks overlap. The cost is queueing. In the
`1` row the Calibre job waited about 76 s behind the OCR job; with the slot off it finished in
5 s. Even with the slot off, the worst mix fits in 1.24 GB.

### Core only, 2 GB: `FILEX_CONCURRENCY` (3 reps)

Three 200 MB grainy scans were sent to pdf.compress at once.

| `FILEX_CONCURRENCY` | Last job done, s | Step s each | worker-core peak | Stack peak | Failed / OOM |
|---|---|---|---|---|---|
| 1 | 38.5 (38.0-41.1) | 12.0 | 504 MB | 756 MB | 0 / 0 of 9 |
| 2 | 29.6 (27.6-30.1) | 13.6 | **768 MB = its limit** | 1028 MB | 0 / 0 of 9 |

Two steps at once finish the batch 23% sooner on 2 CPUs. However, worker-core then sits at its
768 MB limit and only page-cache reclaim keeps it from an OOM kill. With bigger inputs or a
weaker disk, that would become an OOM. During the three 200 MB uploads the api peaks at
260-268 MB of page cache against its 256 MB limit; that cache is reclaimable, and there were no
OOMs. Its anonymous memory stays under 60 MB, well inside the spec's 200 MB upload target.

### Calibre long-book cap

`ebook.convert` to PDF refuses a book whose estimated length is over `pdf_page_cap`. With the
current `MEMORY_MB = 900` and `FILEX_MEM_EBOOK=1g` that cap is 230 estimated pages. The sweep
runs `ebook-convert` the same way the step does (RLIMIT_DATA on the process tree, fresh config
dirs, headless Qt, 300 s timeout) in the worker-ebook image, at 2 CPUs, 3 reps each. RLIMIT_DATA
is `MEMORY_MB` + 64, the runner's step overhead.

| RLIMIT_DATA | Container | Est. pages | Result | PDF pages | Time s | Peak MB |
|---|---|---|---|---|---|---|
| 964 (900 + 64) | 1024 | 150 | ok | 173 | 2.3 | 595 |
| 964 | 1024 | 230 | ok | 265 | 3.7 | 829 |
| 964 | 1024 | 300 | ok | 345 | 4.8 (3.9-6.0) | 1024 (at the limit) |
| 964 | 1024 | 400 | **hangs to the 300 s timeout, OOM kills** | 0 | 300 | 1024 |
| 964 | 1024 | 475 | **hangs to the 300 s timeout, OOM kills** | 0 | 300 | 1024 |
| 1600 (1536 + 64) | 1536 | 300 | ok | 345 | 4.0 | 1027 |
| 1600 | 1536 | 400 | ok | 461 | 5.3 | 1309 |
| 1600 | 1536 | 475 | ok | 549 | 5.8 | 1520 |
| 1600 | 2048 | 400 / 475 | ok / ok | 461 / 549 | 5.2 / 5.7 | 1309 / 1520 |

- **Memory per page:** about 2.8 MB per estimated page, on a base of about 185 MB.
  `pdf_page_cap`'s 300 MB base and 2.6 MB per page are conservative up to about 400 pages, and
  right at the edge at 475 (predicted 1535 MB, measured 1520 MB).
- **A book that is too big does not fail fast.** Calibre's renderer is OOM-killed and
  `ebook-convert` waits out the full 300 s, holding the heavy slot the whole time. So the
  up-front cap is what keeps other heavy jobs moving, and it has to stay.
- **Estimates vs real pages:** on this plain-prose book, an estimated page is about 1.15 real
  PDF pages (230 est. = 265 PDF pages). The "~175 Calibre pages" in the `ebook_convert`
  docstring came from a different text; real books vary.

## What fails or is too slow at 2 GB

Nothing in the representative set failed at the 2 GB / 2 CPU cap, with all three optional
profiles on. The limits are these:

1. **The host OS is not in the 2 GB.** The cap covers the stack only. A real 2 GB box also runs
   its OS, dockerd and maybe other apps, often 400-700 MB together, which leaves the stack about
   1.3-1.6 GB. The measured worst cases are 1.05 GB with the heavy slot on and 1.24 GB with it
   off: on a real 2 GB box the slot is required, and all profiles is the edge.
2. **Long books to PDF.** Over about 300 estimated pages, a 1 GB ebook worker cannot finish; it
   hangs 300 s. The current cap (230 est.) keeps this from happening.
3. **Concurrency 2 on core.** It works, but worker-core runs at its 768 MB limit with
   200 MB-class inputs.
4. **Slow but working:** OCR of 50 scanned pages takes 75 s here, about 1.5 s per page, against a
   target of 8 s per page. pdf.to-docx of a 500-page PDF takes 34 s, single-threaded. Both run
   2-3x slower on a low-power CPU ([CPU note](#cpu-note)).

## Recommendations

| Setting | 2 GB box | 4 GB box |
|---|---|---|
| `COMPOSE_PROFILES` | empty (core) by default; **one** of `office`, `ocr`, `ebook` is safe; all three fit in testing (peak 1.05 GB) but leave no margin once the OS is counted | `office,ocr,ebook` |
| `FILEX_HEAVY_SLOTS` | `1` (required) | `1`. `0` is safe on memory (1.24 GB worst measured) and stops a Calibre or Office job waiting behind a long OCR run, so turn it off when wait time matters more than headroom |
| `FILEX_CONCURRENCY` | `1` for every group | core `2` (23% faster batches, needs `FILEX_MEM_CORE=1g` or more); office `1` (security review L-2); ocr `1` (OCRmyPDF already uses its CPUs per job); ebook `1` |
| `FILEX_MEM_CORE` | `768m` (the measured core peak is 504 MB with concurrency 1) | `1g` |
| `FILEX_MEM_OFFICE` | `1g`, or `512m` if memory is tight (measured peak 209 MB) | `1g` is plenty; `1536m` is not needed for these inputs |
| `FILEX_MEM_OCR` | `1g` (50 pages peak at 475 MB) | `1g`-`1536m` |
| `FILEX_MEM_EBOOK` | `1g` | `1536m`, together with the Calibre change below |

**Calibre cap: raise `MEMORY_MB` from 900 to 1536.** The cap is
`min(MEMORY_MB, container limit)`, so a box that keeps `FILEX_MEM_EBOOK=1g` keeps a 1 GB-based
cap. Measured, 300 estimated pages succeed in a 1 GB container (the formula allows 278). A box
with `FILEX_MEM_EBOOK=1536m` gets about 475 estimated pages, about 550 PDF pages, in under 6 s,
with 3 of 3 passing. Do not raise it further without raising `FILEX_MEM_EBOOK` too: at 475
pages the peak is 1520 MB, so 1.5 GB is the useful ceiling. Two follow-ups make the step safer:

- Add 10-15% headroom to `PDF_MB_PER_PAGE` (2.6 → 2.9) so that the top of the range is not at
  the limit.
- Fail fast when the container is near its limit, instead of waiting out the 300 s timeout
  (doc-engineer). For example, watch `memory.events` for `oom_kill`.

Both changes belong to doc-engineer (code) and devops (`.env.example`, ADR-0002 table). This
benchmark only measured them.

**ADR-0002 / spec 5.1 numbers to replace:**

| Item | Estimate | Measured |
|---|---|---|
| Worst case, default limits, all profiles | ~3.1 GB | 1.05 GB (slot on), 1.24 GB (slot off), stack only |
| Worst case, low-memory preset | ~2.4 GB | the same 1.05 / 1.24 GB: the limits cap, they do not reserve |
| Core-only worst case | ~1.1 GB | 0.76 GB (concurrency 1), 1.03 GB (concurrency 2) |
| Idle per optional worker | ~150 MB | 30-32 MB |

### Spec 5.1 targets

| Target | Result |
|---|---|
| Idle core ≤ 350 MB | 83 MB: met |
| Idle per optional worker ≤ 150 MB | 30-32 MB: met |
| Peak with `office,ocr,ebook` on 4 GB never OOMs | 0 OOM kills in 138 jobs at 2 GB and 4 GB: met |
| Tiny box, core only, every core tool runs | the core tools in this set (merge, compress including 200 MB, to-docx 500 p) run at 2 GB, peak 0.76 GB: met. Not every core tool was run; the `tests/e2e` suite covers the rest functionally |
| Job overhead ≤ 0.5 s | 0.01-0.3 s: met |
| pdf.merge 2 x 10 p ≤ 3 s | 0.6 s: met |
| pdf.compress 50 p scan ≤ 60 s, output ≤ 50% | 2.0 s, 17% of input ([compress-baseline.md](compress-baseline.md)): met |
| office.to-pdf 20 p DOCX ≤ 20 s | 1.6 s: met |
| ocr.pdf ≤ 8 s per page | 1.5 s per page (300 dpi, eng): met on the dev PC; probably still met at 2-3x slower |

### CPU note

The dev PC's cores are desktop-class. Low-power x86-64 home-server chips are typically 2-3x
slower single-threaded. That was **not measured**: `cpu.max` caps how much CPU the stack gets,
not how fast each core is. On such a box expect about 3-5 s for OCR per page, 70-100 s for a
500-page pdf.to-docx, and every target above except OCR with large margins. Rerun
`weak_hardware.py stack` on the real box to confirm.
